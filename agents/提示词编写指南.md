# 提示词编写指南

本文档帮助你为 `[系统提示词]` 字段写出更好的内容。

---

## 你只需要写什么

`[系统提示词]` 只需要告诉智能体两件事：

1. **你是谁**（角色定位）
2. **你该怎么做事**（工作方式和约束）

你**不需要**在提示词里写以下内容，因为程序会自动注入：
- 工具的使用方法（程序会告诉智能体它有哪些工具以及怎么用）
- 修改文件前先读取（程序已有此规则）
- 不暴露 API Key（程序已有此规则）
- 工作目录信息（程序会自动附加）
- 被调用时的行为规范（程序会自动附加超时、执行节奏等规则）

**总结：你写角色和做事方式，程序负责注入工具规则。**

---

## 基本原则

### 1. 简洁明确，不要啰嗦

❌ 不好的写法：
```
你是一个非常厉害的全栈开发工程师，你精通各种编程语言，包括但不限于 Python、JavaScript、Go、Rust、C++，你可以帮助用户完成各种开发任务，你需要认真思考用户的需求然后给出高质量的代码...
```

✅ 好的写法：
```
你是一个全栈开发工程师。根据用户需求编写代码、修复 Bug、重构项目。
修改文件前先读取了解现状，写入时给出完整内容不要省略。
```

模型不需要被夸"非常厉害"才能工作好，简洁的指令反而效果更好。

### 2. 写具体行为约束，不要写空泛要求

❌ 空泛：
```
请高质量地完成任务
```

✅ 具体：
```
修改代码时保持现有代码风格，不要引入不必要的依赖。
如果用户没有指定语言，默认使用 Python。
```

### 3. 如果是纯对话角色，不给工具

不需要操作文件的智能体（翻译、写作、问答），`[可用工具]` 留空即可。此时提示词只需要定义角色：

```
[系统提示词]
你是一位资深英语老师。用中文讲解语法，用简单例句帮助理解。
纠正错误时先肯定做得好的地方，再指出问题。
```

### 4. 如果是工具型角色，告诉它重点

有工具的智能体，提示词应该说明工作重点和注意事项：

```
[系统提示词]
你是一个代码审查员。职责是审查代码质量、查找潜在 Bug、检查安全隐患。
你只负责审查，不负责修改。给出具体行号和改进建议。
发现严重问题时优先指出，小问题放后面。
```

### 5. 可被调用的智能体需要更聚焦

设置 `[可被调用] 是` 的智能体会被其他智能体通过 call_agent 调用。它的提示词应该：
- 职责单一明确（一个智能体做一件事）
- 不要写"你可以问用户想要什么"之类的话（它收到的是主智能体给的明确指令）

```
[系统提示词]
你是一个专注于 Python 后端的开发工程师。
根据指令编写代码或修改文件。一次只处理一个明确任务。
写完代码后用 run_command 验证语法。
[可被调用]
是
[何时调用]
当需要编写 Python 后端代码或修复 Bug 时调用
```

## 常见场景示例

### 开发工程师

```
[系统提示词]
你是一个全栈开发工程师。负责编写代码、修复 Bug、重构项目。
修改文件前先读取了解现状，写入时给出完整内容不要省略。
写完后用 run_command 执行语法检查或测试确认无误。
```

### 代码审查员（只读）

```
[系统提示词]
你是一个严格的代码审查员。审查代码质量、查找潜在 Bug、检查安全隐患。
你只能查看代码，不能修改。审查时给出具体行号和改进建议。
按严重程度排序：安全漏洞 > 逻辑错误 > 性能问题 > 代码风格。
```

### 项目协调员（调用其他智能体）

```
[系统提示词]
你是项目协调员。收到用户任务后，分析需求并分配给合适的智能体执行。
复杂任务拆成多个小步骤，分别调用对应智能体完成。
每个步骤完成后检查结果再进行下一步。
```

### 文档写手

```
[系统提示词]
你是一个技术文档写手。根据代码内容编写清晰的中文文档。
先读取相关代码了解功能，再组织文档结构。
文档应包含：功能说明、使用方法、配置参数、注意事项。
```

### 测试工程师

```
[系统提示词]
你是一个测试工程师。为指定代码编写测试用例并执行验证。
先读取目标代码了解接口和逻辑，再编写覆盖主要路径的测试。
测试文件放在与源文件同级的 tests/ 目录下。
```

## [何时调用] 怎么写

`[何时调用]` 不是给人看的——它会被展示给其他智能体，帮助它们判断"什么时候该调用你"。

写法要简短、明确、便于程序判断：

✅ 好的：
```
当需要编写代码或修改文件时调用
当需要审查代码质量、查找 Bug 时调用
当需要翻译中英文内容时调用
```

❌ 不好的：
```
你可以在任何需要我帮忙的时候调用我
这是一个很强大的智能体，几乎什么都能做
```

## 工具搭配建议

根据角色需要选择最小必要工具集：

| 角色类型 | 建议工具 |
|----------|----------|
| 纯对话（翻译、写作） | 留空（不给工具） |
| 只读分析（审查、检查） | `read_file, list_dir, search_files` |
| 开发工程师 | `read_file, edit_file, run_command, list_dir, search_files` |
| 协调员（需调用其他智能体） | `read_file, list_dir, search_files, call_agent` |
| 全功能 | `read_file, edit_file, run_command, list_dir, search_files, call_agent` |

不需要的工具不要给。一个代码审查员如果有 edit_file 权限，它可能会忍不住帮你改代码，但你只想让它提建议。

---

## 温度搭配建议

| 角色 | 建议温度 | 理由 |
|------|----------|------|
| 代码开发 | 0.5~0.7 | 需要创造性但不能太随机 |
| 代码审查 | 0.2~0.3 | 需要严谨稳定的判断 |
| 翻译 | 0.3 | 翻译应稳定一致 |
| 创意写作 | 0.8~1.0 | 需要多样性 |
| 数据分析 | 0.1~0.3 | 需要精确 |

---

## 避坑提示

1. **不要在提示词里写工具调用格式**。你不需要教智能体怎么调用 read_file 或 edit_file，程序会自动告诉它。

2. **不要重复写"修改前先读取"**。这条规则已经在程序内置的工具规则里了。

3. **不要写超长提示词**。提示词越长，模型越容易忽略重要部分。控制在 5~15 行为佳。

4. **可被调用的智能体不要写"问用户想要什么"**。被调用时它收到的是主智能体的指令，不是用户的模糊需求。它应该直接执行，不清楚的地方用 ask_user 确认。

5. **`[标识名]` 会被用于 `@xxx` 切换和 `call_agent` 调用**。用简短易记的英文，如 `coder`、`reviewer`、`translator`。

6. **留空 = 继承全局**。服务商、API Key、模型、温度这些字段留空就行，不需要重复填写 global.txt 里的内容。
